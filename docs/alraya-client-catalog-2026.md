## 2) منطق الكتالوج عند الراية

الراية تعمل بأسلوب:

```
باقة رئيسية (العرض الرئيسي)
  + إضافات اختيارية حسب المشهد
      (حديقة، زفة، سهرة شباب، غداء، برومو، رافعة، كاميرا إضافية…)
```

- عمود **المبلغ** = سعر العرض الحالي للزبون  
- عمود **بدل** = سعر مرجعي أعلى (للمقارنة التسويقية) — إن وُجد  
- هذا أقرب لنموذج: `Service` / مشاهد + `Offer` بأسعار، ويمكن تمثيل الإضافات كعروض منفصلة أو `SubService` حسب قرار المرحلة 3

**تميّز عن وميض:** وميض يركّز على مناسبة→نوع جمهور→باقة (عادي/VIP). الراية تركّز على **رئيسي + إضافات مشهد**.

## 4) اتفاقية عمل تصوير — الحقول والبنود

نموذج مرقّم (مثال على الورق: **000020**).

### حقول تُملأ يدوياً على الورق → مقابل النظام

| حقل الورق | كيان مقترح |
|-----------|------------|
| التاريخ | `Event.createdAt` أو تاريخ العقد |
| الطرف الثاني (الاسم) | `Customer` |
| العنوان / رقم الهوية | `Customer.address` + حقل هوية لاحقاً إن لزم |
| توقيع الطرف الثاني | خارج MVP أو مرفق لاحقاً |
| المبلغ المتفق عليه | `Event.totalPrice` |
| المبلغ المدفوع | مجموع `Payment` |
| تاريخ التصوير | `EventService.startsAt` (**مصدر التقويم**) |
| ملاحظات | `Event.notes` |
| آخر موعد للاستلام | Setting أو حقل لاحق على المناسبة |
| ختم الاستوديو | ورقي |

### ملخص البنود الـ 13 (مرجع شروط — ليس كلها شاشات MVP)

1. لا مسؤولية عن الفيديو/الصور بعد **30 يوماً** من تاريخ التصوير  
2. مسؤولية عطل المعدات أثناء التصوير محدودة بخصم جزء الفشل  
3. دفع **كامل** المبلغ المتفق قبل بدء العمل  
4. صاحب الحفلة مسؤول إن واجه الطاقم مشاكل أثناء العمل  
5. توفير وسائل راحة للطاقم — وإلا النتيجة على صاحب الحفلة  
6. المواصلات على الزبون إلا قاعات **داخل مدينة دورا**  
7. المبلغ قابل للزيادة أو النقصان  
8. لا تسليم قبل السداد الكامل  
9. احتساب التصوير بالصورة أو ضمن العرض المتفق  
10. الاتفاقية ملزمة بعد التوقيع — لا إلغاء بند  
11. تأجيل الموعد → المبلغ المدفوع يُحجز للموعد الجديد  
12. إلغاء المناسبة → لا مطالبات مالية من الزبون على الاستوديو  
13. إبراز هذه الاتفاقية عند استلام الصور/الفيديو  

> **للمبرمج:** البنود تُترجم لاحقاً لنص شروط في العقد/المناسبة أو صفحة إعدادات. لا تبني وحدة قانونية كاملة في MVP إلا بطلب المدير.

## 5) ربط بهيكل البيانات الحالي

```
Customer (الطرف الثاني)
  └── Event (مناسبة + totalPrice + notes)
        ├── EventService[]   ← كل موعد تصوير/مشهد (رئيسي، زفة، سهرة…) بتاريخ → التقويم
        └── Payment[]        ← المدفوع مقابل «المبلغ المدفوع» على الاتفاقية
Offer / Service              ← صفوف جدول عروض 2026
```

**قاعدة ذهبية بلا تغيير:** أي بند له تاريخ تصوير = `EventService` ظاهر على `/admin/calendar`.

## 6) ماذا تفعل نهلة بهذا الملف؟

1. عند **مرحلة 3 (كتالوج):** املئي الخدمات/العروض من الجدول أعلاه (أو راجعي المطابقة مع ما بُني).  
2. عند **مرحلة 4:** تأكدي أن إضافة خدمة مناسبة يمكن أن تمثل «رئيسي + إضافات».  
3. عند **مرحلة 6 (دفعات):** راعي شرط «لا تسليم قبل السداد» كقاعدة عمل (حتى لو التسليم الرقمي لاحقاً).  
4. لا تنسخي أسعار وميض — **أسعار الراية من هذا الملف**.
