القانون الذهبي هيكل النظام دورة كل مرحلة المراحل 0→9 التقويم بعد الإطلاق الصيانة قواعد Cursor

! القانون الذهبي (غير قابل للتفاوض)

ممنوع

  • أزرار/روابط ظاهرة صامتة أو href="#"
  • الانتقال لمرحلة تالية قبل بوابة اختبار يدوي ناجحة
  • خلط مرحلتين في نفس الوقت
  • اعتماد أعمى على الذكاء الاصطناعي بدون فهم
  • تنفيذ الوكيل قبل أن تكتب نهلة: تم ثم نفّذ

إلزامي في كل مرحلة

  • هيكل كامل ظاهر لما يخص المرحلة
  • تدفق بيانات مغلق: واجهة → تحقق → MySQL → عرض
  • اختبار يدوي + توقيع بوابة
  • إشعار واتساب: node tools/pm-notify.mjs gate ...
  • رفع GitHub بعد بوابة ناجحة عند تفعيل GIT_AUTO_PUSH=1

⌂ هيكيلة النظام (سطحان)

1) لوحة الإدارة /admin/*

  • ثيم NexLink — RTL
  • الثيم: Light افتراضي + Dark عبر زر theme-btn
  • أهم شاشة تشغيل: التقويم /admin/calendar
  • زبائن · مناسبات · خدمات · دفعات · Inbox حجوزات · رسائل · إعدادات
موظف← Auth← Admin Shell← Prisma← MySQL

2) الموقع العام (لاندينغ)

  • هوية استوديو الراية (عنابي + ذهبي)
  • حجز عرسان أونلاين /book
  • تواصل معنا /contact
  • واتساب عائم + روابط سوشيال من الإعدادات
زائر← /book← BookingRequest← تحويل أدمن← تقويم

↻ دورة عمل المبرمجة في كل مرحلة

1. اقرأdocs المرحلة + القواعد
2. خطّةالوكيل يعرض خطة فقط
3. تم + نفّذبعد الفهم فقط
4. ابنِ + اختبريدوياً أنتِ المسؤولة
5. بوابةgate واتساب ثم المرحلة التالية
دور الوكيل: مساعد + معلّم (نهلة تحت تدريب وتطوير). ممنوع: ثقة عمياء بالذكاء الاصطناعي. أي كود لا تشرحينه في دقيقتين = غير مقبول.

★ معيار النجاح الذهبي — التقويم

أي حجز/موعد له تاريخ يجب أن يظهر في /admin/calendar.

المصدريظهر على التقويم؟
EventService بتاريخنعم — إلزامي
تحويل حجز أونلاين → مناسبةنعم — فوراً بعد التحويل
موعد من Modal التقويمنعم — إلزامي
طلب PENDING لم يُحوَّللا (Inbox فقط)

موعد في قاعدة البيانات وغير ظاهر على FullCalendar = فشل المرحلة.

→ المراحل الإنتاجية 0 ← 9

كل سهم بين مرحلتين = اختبار يدوي ناجح + توقيع بوابة + إشعار واتساب.

0

تأسيس المشروع وقاعدة البيانات

Next.js يعمل محلياً + Prisma ↔ MySQL + جداول MVP

بوابة 0npm run devmigrate
  • Scaffold Next.js + TypeScript
  • Prisma schema + migrate على MySQL
  • .env / .env.example جاهزان
  • اختبار: localhost + اتصال DB + جداول موجودة
1

شِل الأدمن + الثيم

NexLink RTL · Light افتراضي · theme-btn · شعار الراية · لا أزرار ميتة

بوابة 1theme-btnRTL
  • Layout أدمن + أصول محلية (لا CDN ديمو)
  • Light افتراضي / Dark بالزر + حفظ localStorage
  • سايدبار: الظاهر يعمل أو مخفي حتى مرحلته
2

المصادقة (Auth)

دخول/خروج حقيقي + حماية /admin/*

بوابة 2جلسةmiddleware
  • صفحة login + مستخدم seed
  • غير المسجّل يُحوَّل لـ login
  • Logout يدمّر الجلسة
3

الكتالوج (خدمات + باقات)

CRUD للخدمات/الباقات المرتبطة بالحجز والمناسبات

بوابة 3CRUD
  • إنشاء/تعديل/عرض خدمات وأسعار
  • بيانات تُحفظ في MySQL وتظهر بعد Refresh
  • لا نماذج حفظ صامتة
4

الزبائن + المناسبات + خدمات المناسبة

أساس بيانات المواعيد التي ستظهر لاحقاً على التقويم

بوابة 4 يغذّي التقويمCustomer / Event
  • زبائن CRUD
  • مناسبات + EventService بتواريخ
  • مسار بيانات جاهز للمرحلة 5
5

التقويم (FullCalendar) — الأهم تشغيلياً

كل المواعيد الحقيقية ظاهرة · فشل الظهور = فشل المرحلة

بوابة 5 معيار منتج/admin/calendar
  • عروض شهر/أسبوع/يوم
  • كل EventService بتاريخ يظهر كحدث
  • Modal إضافة/تعديل يكتب DB ويحدّث فوراً
  • تحقق يدوي بعد Refresh
6

الدفعات والخصومات

المتبقي = السعر − الخصم − المدفوع (مصدر واحد في الخادم)

بوابة 6PaymentDiscount
  • إضافة دفعة/خصم يحدّث المتبقي فوراً
  • رفض مبالغ 0 أو سالبة
  • الأرقام ثابتة بعد Refresh
7

الحجز الأونلاين (لاندينغ + Inbox)

زائر يسجّل → الإدارة تحوّل → مناسبة + ظهور فوري على التقويم

بوابة 7 يغذّي التقويم/book
  • لاندينغ + نموذج حجز + صفحة شكر
  • Inbox طلبات في الأدمن
  • التحويل ينشئ Customer + Event + EventService
  • الموعد يظهر على التقويم فوراً
8

تواصل معنا + سوشيال + واتساب عائم

رسائل ContactMessage + إعدادات الموقع (لا قيم صلبة في الفرونت)

بوابة 8/contactsettings
  • نموذج تواصل → Inbox رسائل
  • واتساب عائم من الإعدادات
  • إخفاء أيقونة سوشيال إن الرابط فارغ
9

الداشبورد + تثبيت القائمة + إطلاق MVP

مؤشرات حقيقية + جولة سيناريو كاملة + لا روابط ميتة

بوابة 9 · إطلاقDashboard
  • بطاقات من DB حقيقية
  • سيناريو عرسان كامل حتى المتبقي 0 + تقويم
  • مرور على كل روابط السايدبار
  • تجربة موبايل أساسية للاندينغ والحجز

+ بعد الإطلاق (ليس قبل إغلاق بوابة 9)

🛠 التشغيل الإنتاجي والصيانة

بعد التسليم — تشغيل يومي

  • مراقبة التقويم والحجوزات الجديدة
  • متابعة Inbox الطلبات والرسائل
  • نسخ احتياطي لقاعدة MySQL بشكل دوري
  • مراجعة إعدادات واتساب/سوشيال
  • تتبع الأخطاء (لوجات / تقارير مستخدم)

صيانة وتطوير مستمر

  • إصلاح عيب = فرع صغير + اختبار يدوي + gate إن لزم
  • تحسينات V2 فقط بعد استقرار MVP
  • تحديث الاعتماديات بحذر مع اختبار شاشات حرجة
  • أي توسّع خارج الخطة يحتاج موافقة مصطفى
  • نفس أسلوب تم / نفّذ مع الوكيل في الصيانة
تعريف صيانة ناجحة: التعديل لا يكسر التقويم، لا يُظهر أزراراً ميتة، ولا يتجاوز مرحلة غير مكتملة البوابة.
